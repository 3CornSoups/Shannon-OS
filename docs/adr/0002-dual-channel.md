# ADR-0002: 预判器前置 + 双通道设计

## 状态

~~已采纳（2026-05-12）~~ **已被 ADR-0005 替代（2026-05-14）**。预判器已移除，委托决策完全由 LLM 通过 tool calling 自主判断。

## 背景

PRD 定义了「规则预判 + LLM 确认」两阶段决策。设计讨论中出现了两个关键选择：

1. 预判器应该在 LLM 调用之前还是之后运行？
2. 不懂编程术语的小白用户如何触发委托？

## 决策

### 预判器前置

预判器在 LLM 调用之前运行，命中后发送 delegate_confirm_required 事件并阻塞等待用户选择：

- 用户确认 → 构造 ReActDelegate → **直接执行委托（跳过 LLM）**
- 用户拒绝/超时 → 不注入委托提示 → LLM 调用 → 正常 Agent 流程
- 预判器未命中 → 注入弱委托提示 → LLM 感知通道兜底

理由：用户确认后不应再由 LLM 二次判断。预判器已经判断适合 + 用户确认，LLM 无权推翻此决定。

### 双通道设计

| 通道 | 触发条件 | 行为 |
|------|---------|------|
| 规则快通道 | 关键词命中（强代码工程信号 + 长度/多文件条件） | 注入强委托提示到 system prompt |
| LLM 感知通道 | 始终启用 | system prompt 包含委托能力描述，LLM 可自行建议委托 |

规则快通道的预判器设计为保守型——必须同时满足两个条件才触发：
1. 包含强代码工程信号词（重构/refactor、提取公共/extract、拆模块/split module 等）
2. 用户输入长度 > 80 字符或明确提到多文件

排除场景：纯 git 只读、单文件简单修改、纯查询/监控类请求。

## 后果

### 正面
- 用户明确选择委托或基础 Agent，UI 与后端状态一致
- 确认后 LLM 收到强指令（risk_level=LOW），自动委托无需二次确认
- 预判器保守，宁漏判不误判，减少不必要的确认弹窗
- LLM 感知通道兜底：预判器未命中但 LLM 判断适合委托时，仍可触发确认

### 负面
- 预判命中后阻塞等待用户操作（默认 300s 超时），用户离开时体验差
- 预判器和 LLM 提示词需要维护一致性
- 保守预判器可能导致部分适合委托的任务未被识别（由 LLM 通道补偿）
